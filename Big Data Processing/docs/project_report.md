# ETL-пайплайн витрин

## 1. Общая информация

Цель проекта — построить ETL-пайплайн на PySpark, который читает данные о пользовательских сессиях и контенте из S3, выполняет очистку и исследовательский анализ, формирует пять витрин и сохраняет их обратно в S3 в формате Parquet.

- Spark: 3.5.1;
- Java: 17;

Результаты проверки относительно 31 668 строк справочника:

|---|---:|---:|

- отсутствующая или неположительная длительность контента заменяется медианной длительностью для соответствующего типа контента

## 5. Построенные витрины

### 5.1. `user_content_mart`

Гранулярность: пользователь — произведение.

Основные расчёты:

- суммарные часы и количество уникальных сессий;
- доля завершённости `total_hours / main_content_duration_hours`, ограниченная сверху единицей;
- признак завершения при `finished_percent >= 1`;
- первая и последняя даты взаимодействия;
- `days_spent` рассчитывается как календарный интервал между первой и последней датой плюс один;
- средняя длительность сессии.

Важно: согласно реализованной формуле `days_spent` — это длительность календарного интервала, а не количество различных активных дат внутри интервала.

### 5.2. `user_genre_mart`

Гранулярность: пользователь — жанр. После `explode()` рассчитываются часы, сессии, завершённые произведения, количество взрослого и детского контента. Ранг жанра задаётся внутри пользователя по убыванию часов, затем числа сессий.

### 5.3. `user_mart`

Гранулярность: пользователь. Витрина объединяет общую активность, количество контента и жанров, среднюю завершённость, последние взаимодействия и любимые измерения пользователя.

Любимый жанр, тип контента и платформа выбираются по суммарному времени; при равенстве используются количество сессий и затем алфавитный порядок.

### 5.4. `content_mart`

Гранулярность: произведение. Содержит количество пользователей, общее время, средний процент завершённости, число фактически использованных платформ и относительную популярность.

`platforms_count` отражает число платформ, на которых контент встречался в событиях рассматриваемой выборки, а не полный перечень платформ, где произведение технически доступно.

### 5.5. `daily_user_mart`

Гранулярность: пользователь — дата. Содержит число уникальных произведений, часы, количество сессий и день недели.

Перед сохранением для каждой витрины проверяется отсутствие повторов по её ключу.

## 6. Анализ плана выполнения `user_mart`

В физическом плане Spark использует несколько типов соединений. Исходные события объединяются
со справочником контента через Inner BroadcastHashJoin по main_content_id, поскольку таблица
content достаточно небольшая. Таблица медианных длительностей также присоединяется через
LeftOuter BroadcastHashJoin. Однако при итоговой сборке user_mart выполняется с помощью
пяти LeftOuter SortMergeJoin по puid. Дополнительно SortMergeJoin используется при соединении
пользовательско-контентных агрегатов с жанрами по main_content_id.

Операции Exchange hashpartitioning возникают при удалении дубликатов по audition_id,
группировках по пользователям, контенту и жанрам, расчётах countDistinct, а также перед
оконными функциями и SortMergeJoin. Эти операции приводят к перемещению данных между
партициями. После Exchange часто выполняется Sort, поскольку для merge-соединений и оконного
ранжирования данные должны быть отсортированы.

Наиболее дорогими выглядят пять итоговых SortMergeJoin, многостадийные расчёты countDistinct и
операции с жанрами. Функция explode() увеличивает количество строк, так как для каждого
произведения создаётся отдельная запись на каждый жанр. Оконные функции row_number() для
поиска любимого жанра, типа контента и платформы также требуют перераспределения и сортировки
данных. При этом InMemoryTableScan показывает, что объединённый датафрейм читается из кэша,
поэтому исходные Parquet-файлы не приходится полностью перечитывать для каждой ветви расчёта.

План можно улучшить, если рассчитывать unique_genres_count на основе уже построенной user_genre_mart.
Это позволит избежать повторного explode() и отдельного countDistinct(genre). Таблицу соответствия
контента жанрам также можно получить из небольшого справочника content и передать через broadcast(),
чтобы убрать дополнительный SortMergeJoin по main_content_id. Кроме того, после проверки размеров
можно рассмотреть broadcast для небольших пользовательских агрегатов, присоединяемых к user_mart

## 7. Итоговые выводы

- основная проблема качества — большое число пропусков в `app_version`, однако этот признак не используется в расчёте основных витрин
- найдено 56 аномальных значений в каждой из колонок длительности; они исключены
- в `content` найдены 6 отсутствующих и 1 неположительная длительность; все 7 значений заменяются медианой по типу контента
- соединение по `main_content_id` не размножает строки, а доля сессий без справочника контента составляет около 0.63%
- за весь выбранный период доминировали аудиокниги и платформа «Станция», но максимальное суммарное время наблюдалось в «Букмейт Android»
- многодневная выборка содержит все дни недели и подходит для анализа временной динамики
